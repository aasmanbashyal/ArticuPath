# Frontend development

ArticuPath uses browser ES modules without a frontend build step. The Rust backend embeds `public/` for both browser and desktop mode. New frontend files must also be added to `embedded()` in `desktop-rust/src/server.rs`.

## Module responsibilities

| Module | Responsibility |
| --- | --- |
| `app.js` | Startup, navigation, page rendering, and connecting controllers |
| `state.js` | Shared page and session state, selected model, session updates |
| `events.js` | Delegated clicks, forms, keyboard shortcuts, and navigation actions |
| `recording.js` | Device lifetime, recording, saving, and starting transcription |
| `recording-upload.js` | Ordered chunk uploads, bounded buffering, and retry state |
| `capture-options.js`, `recorder-view.js` | Recording modes and recorder markup |
| `review.js`, `practice.js` | Playback, transcript search/export, script differences, and practice marks |
| `library.js`, `topics.js` | Session list/calendar, metadata, cue cards, and preparation timer |
| `prompter-page.js`, `teleprompter.js` | Script editor/markup and scrolling controls |
| `settings.js`, `appearance.js` | Settings, themes, and desktop window controls |
| `models.js`, `models-view.js` | Model download polling, model list, and setup prompt |
| `feedback.js` | Feedback prompts and provider requests |
| `preferences.js`, `preferences-backup.js` | Browser-profile preferences and portable practice backups |
| `api.js`, `ui.js` | Backend requests, escaping, formatting, shared controls, dialogs, and notifications |

Page modules import the shared state explicitly. Recorder handles, animation frames, and timers remain with their owning controllers. `app.js` passes navigation/render callbacks into the recorder, model manager, and event bindings, so those modules do not import the application entry point. The existing capture constraints, codec choices, and media processing are retained.

## Verification

Run `bun test` for the Rust API and pure-function tests. The test runner builds the full media backend unless `REHEARSE_NATIVE_EXE` points to another freshly built executable. The module-graph test checks imported frontend files against the checkout, catching missing embedded assets and stale desktop builds. The edit tests exercise the current API contract: title, feedback, or tags/cue-card updates are separate requests. See [the API and disk format](api.md).

Install development dependencies with `bun install`. For browser checks, install Chromium with `bunx playwright install chromium`, or set `BROWSER_CHANNEL=chrome` to use installed Chrome. Then run:

```sh
bun run test:ui
```

This command uses Node for Playwright because the Windows Bun runtime stalled when driving the browser. Bun launches Rust and runs the API tests; it no longer implements a backend.

On Windows, set `REHEARSE_NATIVE_EXE` and run `bun run test:ui --desktop` to exercise the actual WebView2 app. Without `--desktop`, a configured native executable runs in `--serve` mode and Chromium connects to it. Each run creates an isolated profile and session folder under `.cadence/ui-check-*`; it never uses the normal desktop profile.

The checks cover all four recording modes, a scripted recording, chunk/save retries, recovery after reloading during capture, import, playback seeking, transcript search, practice marks, feedback prompts, tags, calendar navigation, rename, themes, and practice-backup restore. Browser mode also checks background replacement and actual backup download. Windows native download dialogs are not automated.

Camera and screen frames are generated by canvas, and microphone input uses the browser's fake device. This tests media encoding and composition, but physical-device permissions, the screen-sharing picker, and long recordings still need separate testing. The transcript UI uses a deterministic fixture; the shared API suite separately exercises any locally installed transcription models.

## Measurements

Each UI run writes screenshots and `measurements.json` into its isolated output folder. It records launch-to-recorder time, JavaScript heap usage, recording durations and formats, stop-to-review time, and transcript-seek time. Windows desktop runs also sample memory for the app and descendant processes.

These are development baselines, not a benchmark against the previous implementation. Launch time includes test-browser startup or the WebView2 debugging connection. JavaScript heap excludes browser/native/model allocations, and summed process working sets can count shared pages more than once. Use the same machine, build, and capture conditions when comparing future changes.
